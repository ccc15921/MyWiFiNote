Wi-Fi 7（IEEE 802.11be, EHT）
規格導讀與速查

Wi-Fi 7 以 Extremely High Throughput 為目標：320 MHz、4096-QAM、MRU / Preamble Puncturing，以及最重要的 Multi-Link Operation (MLO)。Wi-Fi 8 的許多可靠度與低延遲機制都建立在這些基礎之上，本頁依 IEEE 802.11be-2024 原文整理。

1Wi-Fi 7 MLO 深入：MLSR / EMLSR / EMLMR（含 STR / NSTR）

Wi-Fi 8 的許多可靠度與低延遲功能，都是建立在 Wi-Fi 7 的 Multi-Link Operation (MLO) 之上。用戶端（non-AP MLD）實際怎麼用多條 link，取決於它有幾顆 radio、以及開啟哪一種 multi-link 模式。本節依 IEEE 802.11be-2024 原文整理（頁碼為 PDF 頁）。

1.1 先釐清名詞：MLSR 不是 spec 用語

802.11be 規格中定義的是 single-radio non-AP MLD 與 multi-radio non-AP MLD（3.2，PDF p.63–65），以及兩種「增強」模式 EMLSR（35.3.17）與 EMLMR（35.3.18）。業界常說的 MLSR（Multi-Link Single Radio）指的是「沒有開啟 EMLSR 的 single-radio MLD」：與 AP MLD 建立多條 link，但同一時間只在一條 link 上收發，換 link 靠一般的省電狀態切換，沒有「多條 link 同時聽、收到誰就切到誰」的機制。

1.2 EMLSR 運作流程

啟用 / 停用

EML Operating Mode Notification 交換

(Re)association 後 EMLSR 預設關閉。non-AP MLD 送 EML OMN frame（EMLSR Mode = 1，EMLSR Link Bitmap 指定 EMLSR links）；AP 應在 Transition Timeout 內回送同內容的 EML OMN 確認。收到確認或 timeout 到期（先到者）即生效。停用流程相同（EMLSR Mode = 0）。

細節：timeout 從 AP 回 Ack 的 PPDU 結束時開始計時；只設單一 link bit 需 AP 宣告 EMLSR Enablement On One Link Support = 1（PDF p.567–569）。
AP 端限制

Initial Control frame 規則

AP 對 EMLSR 用戶端發起交換（group addressed 除外）時，必須先送 MU-RTS Trigger 或 BSRP Trigger，格式為 non-HT / non-HT duplicate、6/12/24 Mb/s；BSRP 的回應限 1 SS。Padding 長度須 ≥ 用戶端宣告的 EMLSR Padding Delay（多個 EMLSR 用戶端時取最大值）。

為什麼：聆聽時每條 link 可能只有 1 根 RX chain，只能可靠解低速 non-HT；padding 給用戶端時間把其他 chain 切過來（PDF p.570、p.572）。
交換期間

單 link 獨佔

回應 initial Control frame 後，用戶端只在該 link 收發，不得在其他 EMLSR link 收發；AP MLD 的其他 AP 也不得在其他 EMLSR link 傳給它。回應後 SIFS 起就必須能接收多 SS 的 PPDU。用戶端自己也可直接用 EDCA 發起 TXOP（不需 initial Control frame）。

限制：EMLSR links 上不得使用 dynamic SM power save（PDF p.568、p.571–572）。
結束判定

何時回到聆聽

以下任一成立即視為交換結束，經 EMLSR Transition Delay 後回到多 link 聆聽：在 aSIFSTime + aSlotTime + aRxPHYStartDelay（aRxPHYStartDelay = 20 µs）內沒收到 PHY-RXSTART；或收到的 PPDU 中沒有給自己的 frame；或沒有在 SIFS 後回應需立即回應的 frame。用戶端自己發起的 TXOP 則在 TXOP 結束後回到聆聽。

AP 對策：若沒收到回應且還想繼續，AP 應在 TXNAV 到期前再送一次 initial Control frame（PDF p.571–572）。

1.5 STR / NSTR：multi-radio 的另一條路

定義（3.2，PDF p.63–65）
NSTR link pair：MLD 在一條 link 傳送時，另一條 link 無法滿足 36.3.21 的接收機要求（自干擾）。STR link pair：不是 NSTR 的 link pair。

AP MLD（非 NSTR mobile AP MLD）所有 link pair 必須是 STR；2.4 GHz 與 5/6 GHz 的 link pair 一律視為 STR（NSTR bit 必為 0）。
NSTR 的通道接入規則（35.3.16.4，PDF p.559–560）
拿到 EDCA TXOP 時，若傳送會干擾同一 MLD 在另一條 NSTR link 上的接收，可以選擇不傳、重新 backoff，或把該 AC 佇列視為空的。另有 PPDU end time alignment（35.3.16.5）、start time sync PPDUs（35.3.16.6）讓兩條 link 同時開始 / 結束傳送，以及 PIFS 內錯誤復原（35.3.16.7）。
能力宣告（35.3.16.2，PDF p.557–559）
Maximum Number Of Simultaneous Links：AP MLD = AP 數 − 1；single-radio non-AP MLD（含 EMLSR）= 0；multi-radio 且要求多 link 時 ≥ 1。NSTR Indication Bitmap 逐 link pair 標示 STR(0)/NSTR(1)。Frequency Separation For STR 可建議做 STR 所需的最小頻率間隔。
動態變化
AP 換 channel 可能讓原本 STR 的 link pair 變成 NSTR。支援 NSTR Status Update 的 MLD 可送 Multi-Link Operation Update Request（Operation Update Type = 4）回報新的 STR/NSTR 狀態。NSTR mobile AP MLD（手機熱點）另見 35.3.19（PDF p.575–578）。

1.6 系統設計重點

RF / 基頻

Chain 切換時間

EMLSR Padding Delay 與 Transition Delay 直接反映 LO/PLL 重設、AGC 收斂、RX chain 重新路由的時間。宣告值越小，AP 開銷越小、延遲越低，但硬體要求越高。

AP 排程

EMLSR 用戶端成本

每次 AP 主動發起都要多付一個低速 MU-RTS/BSRP + padding；AP 需追蹤用戶端「正在哪條 link」，且交換期間其他 link 上對它的流量要暫停或改道。

共存

In-Device Coexistence

EML OMN 的 In-Device Coexistence Activities bit 讓 AP 知道用戶端在 EMLSR links 上有 BT/LTE 等共存活動，AP 可把無回應視為共存事件，而非鏈路變差（PDF p.568、p.570）。

廣播 / Beacon

Group addressed 與 TBTT

EMLSR links 上的 group addressed frames 依 35.3.15 緩衝傳送；用戶端可在 TBTT 收 Beacon。NSTR 用戶端應在另一 link 的 TBTT 前結束 TXOP。

Sounding

Beamforming 回饋

上述 EMLSR 規則同樣適用 sounding 序列；Annex AH 有 EMLSR 下的 non-TB / TB sounding 範例（Figure AH-25～AH-27，PDF p.1016）。

Wi-Fi 8

往 802.11bn 的延伸

802.11bn 討論中包含 EMLSR 的強化（例如降低切換開銷、更彈性的 link 使用），以及 Seamless Roaming 借用 MLD 架構跨 AP。細節以 TGbn 最新 Draft 為準。

2TWT / R-TWT：從省電排程到低延遲保護

TWT（Target Wake Time）在 802.11ah 引入、Wi-Fi 6（HE）普及，用來讓 STA 依約定時間醒來交換資料。Wi-Fi 7 的 R-TWT（Restricted TWT）在 broadcast TWT 之上加上「通道接入保護」，把 TWT 從省電工具變成低延遲流量的資源保留機制；Wi-Fi 8 的 Co-RTWT 再把它延伸到多 AP。頁碼：base = 802.11-2024 PDF 頁、be = 802.11be-2024 PDF 頁。

2.1 TWT 基本觀念（802.11-2024 10.46、26.8）

角色與協商

Individual TWT

STA（TWT requesting STA）與 AP（TWT responding STA）一對一協商。請求端用 Request / Suggest / Demand TWT，回應端用 Accept / Alternate / Dictate / Reject TWT；只有 Accept 才建立協議。每對 STA 最多 8 個協議（TWT Flow Identifier 3 bits）。可在 (Re)Association 時一起協商。

出處：base 10.46.1（PDF p.2354–2359）、26.8.2（PDF p.4054–4058）。
一對多

Broadcast TWT

AP（TWT scheduling AP）在 Beacon 的 broadcast TWT element 宣告排程，以 <Broadcast TWT ID, AP MAC> 識別；ID 0 適用所有 scheduled STA。用 Negotiation Type=2 廣告、=3 加入 / 退出成員。Broadcast TWT Persistence 表示排程還會存在幾個 TBTT，配合 Alternate / Reject 預告參數變更或終止。

出處：base 26.8.3（PDF p.4058–4068）。R-TWT 就是建立在 broadcast TWT 上。

2.2 R-TWT（Restricted TWT，802.11be 35.8）

R-TWT 的目標是「為延遲敏感流量保留一段乾淨的時間」。它沿用 broadcast TWT 的建立流程，但 TWT element 帶 Restricted TWT Parameter Set，並對 BSS 內所有支援 R-TWT 的 STA 加上通道接入限制。

建立

Membership setup（35.8.2，be p.618–619）

依 base 26.8.3 的 broadcast TWT 流程加入，但 TWT element 帶 Restricted TWT Parameter Set。Restricted TWT Traffic Info 以 DL / UL TID Bitmap 指定哪些 TID 屬延遲敏感流量（R-TWT TIDs），且這些 TID 必須透過 TTLM 映射到該 link。AP 應設 Trigger=1。STA 可再用 SCS 送 QoS Characteristics（延遲界限、服務區間等）作為 AP 排程依據。

注意：若 TTLM 更新後 R-TWT TIDs 都不再映射到該 link，membership 自動視為拆除。
廣告

Announcement（35.8.3，be p.619–620）

只要有 membership，AP 就必須在 broadcast TWT element 中宣告 R-TWT 排程。Restricted TWT Schedule Info：0 閒置（無成員或全部暫停）、1 可加入、2 已滿、3 代表同一 multiple BSSID / co-hosted BSSID 組內其他 BSS 的排程（Broadcast TWT ID = 31）。STA 不應請求加入 =2 的排程，且不得加入 =3 的排程。

為什麼要 3：讓同一實體 AP 上的其他 BSS 的 STA 也知道要避開這段時間。
關鍵

通道接入規則（35.8.4.1，be p.620–621）

所有支援 R-TWT 的 non-AP EHT STA（不論是否為成員）當 TXOP holder 時，必須讓 TXOP 在任何 active R-TWT SP 開始前結束；傳送前若時間不夠，要以目前 CW[AC] 重新 backoff（不推進 CW、不影響重傳計數）。AP 的 TXOP 只有在用來傳 R-TWT DL TID 或觸發 R-TWT UL TID 時才能延續進 SP。

MLD 細節：若成員 STA 屬 NSTR / EMLSR / EMLMR links，另一條 link 上的交換需提早 T 結束；T = 0（NSTR）、EMLSR Transition Delay、或 EMLMR Transition Delay。
舊裝置

Quiet interval 與交付順序（35.8.4.2、35.8.5，be p.621–622）

AP 可為每個 R-TWT SP 排一個 1 TU 的 overlapping quiet interval，與 SP 同時開始，讓不懂 R-TWT 的舊 STA 在 SP 開頭靜默；EHT STA 可忽略它。SP 內必須先傳 R-TWT TIDs 的 QoS Data；trigger-enabled SP 中 AP 要先觸發成員，成員組 A-MPDU 時也要先放 R-TWT UL TIDs。

限制：每個 R-TWT SP 最多只能重疊一個 quiet interval；正在傳的 Beacon 可延續進 SP。

2.3 STA ↔ AP 如何建立 TWT / R-TWT：交換的封包

協商細節

Setup Command 的往返規則

Accept 才算成立；Alternate / Dictate 時 STA「應」修改參數再送一次請求（例如接受 AP 給的值）。AP 回應的 Flow ID 可以和請求不同。要改既有協議的參數，就用同一個 Flow ID 再送 TWT Setup。AP 也可以送 unsolicited 的 Accept / Alternate / Dictate，Accept 即直接建立協議；broadcast 情境下 AP 也能在 (Re)Association Response 或 TWT Setup 以 Negotiation Type=3 直接指派成員。

MLD

多 link 時的 TWT Setup

TWT Setup 可以在任何 enabled link 上送。TWT element 的 Link ID Bitmap 指出協議屬於哪條 link（每個 element 只能設 1 bit），Target Wake Time 以該 link 的 TSF 為準；同一個 TWT Setup 可帶多個 TWT element，一次為多條 link 建協議（每條 link 最多出現一次）。回應必須指向相同 link。拆除時 TWT Teardown 帶 MLO Link Information element 指定 link。

出處：be 35.3.24.1（PDF p.583–585）、範例 AH.13（PDF p.1012–1013）。

2.4 MLD 下的 TWT（802.11be 35.3.24，PDF p.583–586）

Individual TWT element 以 Link ID Bitmap 指定要在哪些 link 建立協議；支援 Aligned TWT（Basic Multi-Link element 宣告）時，可用 Aligned TWT Bitmap 要求多條 link 的 SP 起始時間對齊、其他參數相同。Broadcast TWT 也可用 Aligned subfield 宣告跨 link 對齊。這讓 EMLSR / NSTR 用戶端可以把所有 link 的喚醒時間排在一起，其餘時間全部 doze。

TXOP 長度預估

每次傳送前要判斷能否在下一個 SP 前完成（含 Ack / BA），否則 defer；這需要精確的 TSF 與 PPDU 時長計算。

應用

何時用 R-TWT

VR/AR、雲端遊戲、語音 / 視訊會議、工業控制等週期性、有延遲上限的流量；配合 SCS 描述流量特性，配合 TTLM 把 R-TWT TIDs 放到最乾淨的 link。
